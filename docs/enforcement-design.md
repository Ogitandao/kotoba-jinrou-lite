## 0. 前提と既存資産（蒸し返さない）

既に決まっていて、本書では変更しないもの：

- 離脱・放置系（afk トラック）は実装済み：階段
1h→3h→6h→12h→24h、30日クリーンで1段軽減、
レベルは0に戻らない
- ハラスメント・セクハラ系は別トラックで重く
（一発アウト級）。階段の定数は 0010 で仮置き済み：
**7日→30日→無期限**（`kl_penalty_minutes` の
'harassment' = [10080, 43200, -1]、max_step=3）
- 運用は全自動前提（おぎは目視対応をしない）。
通報→機械チェック→しきい値で自動非表示→段階ペナルティ
- 全ペナルティにシステムDM通知（理由カテゴリ・内容・
解除時刻・累積で伸びる旨）。強制退室時はルーム内
システムログも流す
- 異議申し立ては凍結級のみ。スプシで Yes/No→自動反映
＋結果DM。1処分1回まで・判断は最終・回答期限は
約束しない。自動化は Apps Script か Make 無料枠で ¥0

既存の仕組み（本書の設計が乗る土台）：

| 資産 | 実体 | 備考 |
|---|---|---|
| 通報の入り口・保管 | `reports`（0004） | reporter_id / target_user_id / target_kind（'user' 'dm_message' 'room_message'）/ target_ref / reason / detail / status（pending・handled・dismissed）。RLS は自分の通報のみ読み書き。**処理系は未実装**（status は置いてあるだけ） |

## 1. ハラスメント系トラックの全体フロー

### 1.1 対象面と通報の集約単位

機械チェックと通報の対象面（UGC テキスト）：

| 面 | テーブル | 通報 target_kind |
|---|---|---|
| DM | dm_messages | dm_message（既存） |
| 待機室チャット | ww_room_messages | room_message（既存） |
| 対戦中チャット | ww_messages | **game_message（追加）** |
| プロフィール（名前・自己紹介） | profiles | user（既存。チェック対象化は未決定 U7） |
| ユーザー自体（行為全般） | — | user（既存） |

集約単位は3層に分ける：

1. **コンテンツ単位**（メッセージ1件）：非表示の判定は
ここで行う。同一メッセージへの通報は
(reporter_id, target_kind, target_ref) で一意化し、
同じ人の二重通報は数えない
2. **ユーザー単位**（違反者の確定違反件数）：処分の
階段はここで数える。集計窓は**ローリング90日**
（§1.5）
3. **通報者単位**：信頼度の集計（§3）

### 1.2 パイプライン

```
通報 (reports: pending)
│
├─(即時) 対象コンテンツのスナップショットを保存
│ （本人が削除・編集しても証跡が消えないように）
│
├─(定期バッチ: 5分毎) 機械チェック
│ OpenAI Moderation API スコア ＋ NGワード照合
│ → moderation_cases に結果と判定を記録
│
├─ 判定:
│ 即時非表示 / 仮非表示 / 違反確定 / 却下
│
├─ 違反確定 → ユーザー単位で集計 →
│ しきい値到達で kl__apply_penalty(track='harassment')
│ → penalty_until 更新 ＋ システムDM
│
└─ reports.status を handled / dismissed に更新し、
通報者の信頼度へ反映（§3）
```

実行基盤：pg_cron に `moderation-sweep` ジョブ
（5分毎）を追加し、pg_net で Supabase Edge Function
`moderation-run` を叩く。Edge Function が pending の
通報をまとめ、OpenAI Moderation API を呼んで判定・
反映まで行う。Supabase 無料枠（Edge Function の
実行回数）で十分に収まる規模。API 呼び出しに失敗
した通報は pending のまま残し、次回バッチで再試行
（3回失敗したら NGワード＋通報数のみで判定する
縮退モードに落とす）。

### 1.3 機械チェックの方法

**主軸：OpenAI Moderation API**
（モデル `omni-moderation-latest`）

- 料金：Moderation エンドポイントは**無料**
（API キー自体は必要。おぎの OpenAI アカウントで
発行し、Edge Function の Secret にだけ置く）
- 返るもの：カテゴリ別フラグ＋スコア（0〜1）。
使うカテゴリ：`sexual`、`sexual/minors`、
`harassment`、`harassment/threatening`、`hate`、
`hate/threatening`、`violence`、`violence/graphic`、
`self-harm` 系、`illicit` 系
- **適用範囲**：通報されたコンテンツが主対象。
通報されていない通常メッセージの全件チェックは
しない（コスト・誤判定・プライバシー配慮の観点。
送信時フィルタは §1.3 末尾の軽い NG ワードのみ）
- **限界（正直なところ）**：
- 日本語の判定精度は英語より落ちる。煽り・皮肉・
ゲーム内スラング（「雑魚」等）は文脈依存で
スコアに出にくい
- そのため単独では処分確定に使わず、**NGワードと
通報の重みの複合**で判定する（§1.4・§1.5）
- スコアのしきい値は初期値であり、運用しながら
調整する前提（判定ログが moderation_cases に
残るので後から検証できる）

**補助：NG ワード照合**

- サーバー側に NG ワードリスト（重度／軽度の2段）を
持ち、正規化（全角半角・空白・かな表記ゆれの吸収）
してから照合する
- 重度（性的・差別・脅迫の直接表現）ヒットは
Moderation の harassment スコア 0.6 相当として
加算。軽度（暴言寄り）は通報との複合でのみ使う
- リスト自体は DB テーブル（`ng_words`）に置き、
アプリ更新なしで差し替え可能にする。具体的な
ワード一覧は本書には載せない（実装時に別途管理）

**送信時フィルタ（一次防御・軽量）**

- 投稿前に重度 NG ワードだけをチェックし、ヒット
したら送信をブロックして本人にだけ警告文を出す
（「この表現は送信できません」）。これは処分では
なく防御であり、記録も残さない（連投で荒らす
場合は §1.5 の件数に数えない）
- DM の URL 送信拒否（実装済み）と同じ位置づけ

### 1.4 自動非表示のしきい値

コンテンツ単位の判定（初期値。U4 で承認を取る）：

| 条件 | 判定 |
|---|---|
| `sexual/minors` が flagged、または同スコア ≥ 0.3 | **即時非表示＋最優先で違反確定審査**（§1.5 の重大カテゴリ扱い） |
| `harassment/threatening` `hate/threatening` `violence/graphic` のいずれか ≥ 0.7 | **即時非表示**＋違反カウント候補 |
| `harassment` `hate` `sexual` のいずれか ≥ 0.85 | **即時非表示**＋違反カウント候補 |
| 上記スコア 0.6〜0.85、または重度 NG ワードヒット | 単独では非表示にせず、**通報の重み合計 ≥ 3.0 で仮非表示**（§3 の信頼度重み。目安＝通常の通報者3人分） |
| 通報の重み合計 ≥ 3.0（スコアが低い場合も） | **仮非表示**（次回バッチの機械チェックで確定判定） |
| スコア < 0.6 かつ重み < 3.0 | 非表示なし。通報は保留し、同一ユーザーへの通報が増えたら再評価 |

- 「非表示」は削除ではない。対象メッセージを他者
から見えなくし（「（運営により非表示）」の置換
表示）、証跡として moderation_cases に残す。
投稿者本人にはシステムDMで通知する（§5 テンプレ）
- 仮非表示が機械チェックで「違反なし」と確定した
ら、表示を自動で戻す（復旧も自動）

### 1.5 処分確定の条件と階段の適用ルール

**違反の確定**：§1.4 で「違反カウント候補」になった
コンテンツのうち、機械チェックの複合スコアが
確定ライン（即時非表示の条件と同一）を超えたもの、
または仮非表示後に再評価でラインを超えたものを
「確定違反1件」とする。却下された通報は件数に
入れない。

**階段の適用**（ユーザー単位・ローリング90日で
確定違反を数える。`kl__apply_penalty` の harassment
階段 7日→30日→無期限 を流用）：

| 確定違反 | 処分 |
|---|---|
| 重大カテゴリ（sexual/minors、脅迫系の高スコア） の初回 | **即 step1（7日）**。警告を挟まない |
| 通常カテゴリ 1件目 | **警告のみ**（penalty_events に kind='warning'・minutes=0 で記録＋システムDM）。制限はかからない |
| 通常カテゴリ 2件目 | step1（7日） |
| 通常カテゴリ 3件目 | step2（30日） |
| 通常カテゴリ 4件目 | step3（無期限） |

- これは現行の仮置き定数（初回から7日）に
「通常カテゴリのみ警告ステップ」を足す案であり、
**U1 でおぎの判断を取る**（現行どおり一律初回7日
も選択肢）
- 制限の内容は afk と同じ penalty_until 方式
（ゲーム参加・ルーム作成を拒否。ロビー・DM・
フレンドは可）。無期限は penalty_until = NULL ＋
minutes = -1 の既存表現に合わせ、解除は異議
申し立て経由のみ
- 90日の窓を過ぎた確定違反は件数から外れる
（afk の30日軽減とは別に、harassment 側は
「窓の外に出る」方式。階段そのものの軽減を
入れるかは U2）
- 同一ゲーム・同一DMスレッド内の連続発言は、
処分逃れの水増し・逆に一晩の口論での過剰処分を
避けるため、**1エピソード（同一対象面・24時間
以内）は最大2件まで**しか数えない

### 1.6 証跡の保存形式と保持期間

`moderation_cases`（1コンテンツ＝1行）に保存する：

- 対象：target_user_id / 面（surface）/ target_ref /
紐づく report_id 群
- スナップショット：本文のコピー、前後の文脈
（同一スレッドの前後各3件まで）、投稿時刻
- 判定材料：Moderation の全カテゴリスコア（jsonb）、
NG ワードヒット一覧、通報の重み合計
- 判定：decision（none / hidden / warned /
penalized / dismissed）、判定理由コード、
penalty_event_id（処分した場合）、判定時刻
- 通報者側の記録は reports と reporter_stats に分離
し、cases には重みの合計値だけを持つ
（誰が通報したかは処分DMにも出さない）

保持期間（案。U5 で判断）：

- 処分に至ったケース：**1年**
- 非表示のみ（処分なし）：180日
- 却下：90日
- 期限切れは pg_cron の掃除ジョブで自動削除。
ただし異議申し立て対象の処分に紐づくケースは、
申立てが終わるまで削除しない

## 2. マスター放置ルールの処分設計

### 2.1 検出条件

証跡は `rooms.all_ready_at`（満室＋マスター以外の
全員が準備OKになった時刻）が既に記録されている。
これを使い、pg_cron の見回り（ww_sweep と同居可）
で次を全て満たす状態が続いたら「放置エピソード」
として `stall_events` に1件記録する：

1. all_ready_at がセットされてから **T分（初期値
5分）** 経過している
2. まだ満室である（人数が定員ちょうど）
3. マスターが同一人物のまま在席している
（退室・交代があったらエピソード終了）
4. ゲームが開始されていない

- エピソードは (room_id, all_ready_at) で一意。
準備OKが崩れて再び揃ったら、新しい all_ready_at
で別エピソードになる
- マスターが開始した／誰かが退室した／マスターが
交代した時点でエピソードは「未処分のまま終了」。
交代した場合、新マスターに前任の放置は引き継が
ない（all_ready_at は交代時点でリセットされる
前提。実装時に 0014 の挙動と突き合わせる）

### 2.2 自動検出か、通報ベースか

**推奨：ハイブリッド**。自動検出は「証跡の記録」
までで、処分の確定は次のどちらかを必須とする：

- (a) そのルームにいたメンバーから通報があり、
stall_events の証跡と一致する（時刻・メンバー
構成が合う）
- (b) 同一マスターの放置エピソードが**30日以内に
3回**（異なるルーム）累積する

理由：自動検出だけだと「トイレ・回線落ち・家族の
用事」等のやむを得ないケースと区別できず、計画書
の「マスターが放置している部屋が存在すること
自体は仕方ない」というおぎ判断ともずれる。逆に
通報だけだと証跡との照合ができず言い合いになる。
(a) は被害者の声＋機械の証跡、(b) は常習性のみを
拾う形で、どちらも「確証があるケース」に絞れる。

### 2.3 段階案

確定した放置は専用 kind（'master_stall'）で数え、
階段は軽く始める：

| 確定回数（ローリング90日） | 処分 |
|---|---|
| 1回目 | **警告DMのみ**（制限なし。ルールの再掲＋「開始できない事情があるときはルームを解散するか、マスターを譲ってください」の案内） |
| 2回目 | 警告DM＋penalty_events に記録（制限なし） |
| 3回目以降 | afk トラックに合算し、afk の現在階段で step+1（1h〜）を適用＋システムDM |

- 3回目から afk に合算する理由：放置は「ゲームを
成立させない」という点で離脱・放置系と同質で、
専用階段を別に持つより既存の軽い階段に乗せる
方が一貫する。専用階段を新設する案は U3 に残す
- 強制退室のような即時措置はしない（そのルームの
参加者は退室して別ルームへ行けるため、被害は
時間の浪費に留まる）

### 2.4 誤検出の回避

- マスターのハートビートが途絶えている間は
エピソードを「保留」にし、放置に数えない
（回線落ちを罰しない。ハートビート基盤は
0010 の room_members.last_heartbeat_at を流用）
- 満室でなくなった瞬間にエピソード終了（誰かが
見切りを付けて抜けた後は、マスターの責任を
問い続けない）
- ゲーム開始後は当然対象外（all_ready_at は開始で
消費される）

## 3. 誤通報・嫌がらせ通報への対策

競合（あるある人狼）の不満の筆頭に「通報したもん
勝ち感」への不信があった。Lite ではここを設計で
潰すことが信頼の核になる。

### 3.1 通報者の信頼度

`reporter_stats`（ユーザー単位）：

- reports_total / reports_upheld（処分・非表示に
至った通報）/ reports_dismissed（却下された通報）
- trust_score：初期値 1.0。的中 +0.1（上限 2.0）、
却下 −0.2（下限 0.2）
- 新規アカウント（登録7日未満）は一律 0.5 から
始める（捨てアカでの通報工作への対策）

### 3.2 重み付けと集約ルール

- §1.4 の「通報の重み合計」は、通報者の
trust_score の合計で数える（人数ではない）
- **同一対象への多人数通報**：内容が同一・文面が
コピペ同然の通報は、機械チェックの対象を1件に
まとめる（チェックはコンテンツ単位なので自然に
そうなる）。重みは全員分を数えるが、**同一ルーム
の参加者同士**からの同時通報は談合の可能性を
見て重みを半分に割引く（フレンド同士も同様）
- 同一通報者→同一対象への通報は24時間で1回まで
（RPC で制限）。通報自体は1日20件を上限とする

### 3.3 通報濫用そのものへの対処

- 却下が累積10件、または trust_score が 0.3 未満に
なったら**警告DM**（§5 テンプレ）
- 警告後も濫用が続く場合は、通報機能そのものを
30日制限する（reports への書き込みを RPC 経由に
絞り、制限フラグを見る形に実装時に寄せる）
- 悪質な虚偽通報（特定ユーザーへの嫌がらせ目的が
パターンとして明確な場合）は、ハラスメント系の
「通常カテゴリ確定違反」として数える余地を残す
（自動確定はせず、ケースとして記録のみ。
適用するかは U6 と合わせて判断）

### 3.4 透明性（通報者への結果通知）

- 通報を受け付けたら、通報者に受付DM（§5）。
処分・非表示に至ったら「対応しました」の結果
通知DMを送る。**処分の具体的内容（何日凍結等）
は出さない**（晒し・報復の材料にしないため）
- 却下の場合も「確認しましたが、違反は確認
できませんでした」と通知する。無言で終わらせ
ないことが「通報したもん勝ち／通報しても無駄」
の両方の不信を防ぐ

## 4. 異議申し立ての実装設計

### 4.1 対象と導線

- 対象：凍結級のみ＝harassment トラックの step1
（7日）以上の処分。afk 系とマスター放置は対象外
（既存合意どおり）
- 導線：処分通知のシステムDM内に「異議申し立て」
ボタンを置き、アプリ内フォーム（申立て理由の
テキスト入力）から送信する。送信で `appeals`
テーブルに1行作られ、処分DMには受付完了の
システムDMが返る
- 1処分1回まで：appeals.penalty_event_id に一意
制約を張り、二重送信は RPC で ALREADY_APPEALED
を返す
- 申立て期限：処分通知から30日以内（無期限処分は
期限なし）。期限の扱いは U8 の確認事項

### 4.2 スプレッドシートの列設計

おぎが見るシートは「見る＋Yes/No を入れるだけ」
に絞る。自動化が埋める列と、おぎが触る列を分ける：

| 列 | 内容 | 誰が書く |
|---|---|---|
| A | appeal_id（DB の uuid） | 自動 |
| B | 受付日時 | 自動 |
| C | 公開ID | 自動 |
| D | ユーザー名 | 自動 |
| E | 処分種別（ハラスメント） | 自動 |
| F | 段階（1段目=7日／2段目=30日／無期限） | 自動 |
| G | 処分日時 | 自動 |
| H | 解除予定（無期限は「無期限」） | 自動 |
| I | 理由カテゴリ（暴言／性的表現／脅迫 等、詳細な生データは載せない） | 自動 |
| J | 本人の申立て文 | 自動 |
| K | **判断（Yes=解除／No=維持）** ※ドロップダウン | **おぎ** |
| L | 処理状態（未処理／反映済み／DM送信済み／エラー） | 自動 |
| M | 処理日時 | 自動 |
| N | エラーメモ | 自動 |

- シートに証跡の全文（問題の発言そのもの）は
載せない方針を推奨（おぎが目視対応しない前提と
一貫させる。判断材料はカテゴリと段階まで）。
ただし「判断には発言内容を見たい」となる可能性
はあるため、列追加の是非は U8 に含める
- 行の追加は自動化側（DB→シート同期）。おぎが
行を消したり並べ替えたりしても壊れないよう、
処理は appeal_id で照合する

### 4.3 自動化方式の比較（Apps Script vs Make）

| 観点 | Apps Script | Make（無料枠） |
|---|---|---|
| 料金 | ¥0（Google アカウントの無料枠内） | ¥0（無料プラン 1,000 ops/月） |
| シートとの相性 | ネイティブ。onEdit／時間主導トリガーで K 列の入力を即検知できる | ポーリング（無料枠は15分間隔）でシートを読む |
| 1件あたりの消費 | 実行回数・時間の無料上限は個人運用では実質問題にならない | シート読取＋DB更新＋DM送信で数 ops/件。月数十件なら足りるが、無駄なポーリングでも ops を消費する |
| DB への書き方 | UrlFetchApp から Supabase REST／RPC を直接呼べる | HTTP モジュールで同様に呼べる |
| 保守 | スクリプトはおぎの Google アカウントに紐づく。コードの正本をリポジトリに置いて同期する運用が必要 | シナリオは Make 側にのみ存在し、リポジトリ管理できない |
| 秘密情報の置き場 | Script Properties（シート閲覧者には見えない） | Make のコネクション内 |

**推奨：Apps Script**。シートが本拠地である以上
ネイティブ連携が一番素直で、無料枠の制限も
ゆるい。Make は「シートを触らずに済む」利点が
今回の用途では効かない。

秘密情報の扱い（方式共通の推奨）：service_role
キーをそのまま使わず、**異議申し立て処理専用の
RPC** `kl_resolve_appeal(p_appeal_id, p_decision,
p_token)` を用意し、トークン一致時のみ処理する。
トークンは Script Properties に保管する。これで
漏洩時の被害が「申立ての付け替え」だけに限定
される（service_role は DB 全権のため）。

### 4.4 反映処理

Yes（解除）の場合：

1. appeals.status を pending→accepted に原子的
更新（更新できた実行だけが先へ進む＝冪等性の核）
2. 対象 penalty_event を見て penalty_until を
クリアし、profiles.penalty_until を再計算
（他の有効な処分が残っていればその最大値）
3. penalty_events に kind='appeal_lifted' の記録行
（minutes=0、申立て経由であることを残す）
4. 本人へ結果DM（解除）送信 → appeals に
dm_sent_at を記録
5. シートの L/M 列を更新

No（維持）の場合：

1. appeals.status を pending→rejected に更新
2. penalty_events に kind='appeal_rejected' の記録
3. 本人へ結果DM（維持）送信
4. シートの L/M 列を更新

- 段階（step）の巻き戻しはしない：解除されても
「処分歴」としては残り、次回の階段計算には
含める（解除＝処分の取消ではなく執行の終了、
という位置づけ。ここは U8 で確認）
- 処理の途中で失敗したら L 列に「エラー」と
N 列に理由を残し、次回トリガーで再試行する
（status が pending のままなら安全に再実行できる）
