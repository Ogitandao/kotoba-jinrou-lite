# ことば人狼 Lite 期待動作テスト仕様書（初版）

作成：2026-11-28。決定仕様の正本は `docs/handover.md`（追補1〜115）、
`docs/demo-only-specs.md`、`docs/enforcement-design.md`。
本書に書いてあるのは**記録に残っている決定だけ**で、推測で作った
仕様は入れていない。記録にない動作は表に入れず、末尾の
「未定義リスト」に論点として分けてある。

## 目的と使い方

- きっかけ：キックされた側の画面遷移が未仕様・未検証のまま実装され、
  実機で初めて発覚した（追補114/115）。今後は「誰が何をしたら、
  誰の画面がどうなるか」を先にこの表で書き切り、そこから自動検証
  （`scripts/verify-*.mjs`）を起こす運用に変えるための土台文書。
- 各行の読み方：
  - 「期待結果（その人の画面）」＝操作した本人の画面で起きること
  - 「期待結果（相手・第三者の画面）」＝相手・同室者・閲覧者など、
    操作していない側の画面で起きること。**この列が空欄の行は
    「相手側に変化がない」ことが仕様**、という意味で読む
  - 「検証方法」は3区分：
    - **自動（スイート名）**：既存の検証スイートに実際にチェックが
      あるものだけ。スイート名は `scripts/verify-<名前>.mjs` に対応
    - **未実装**：仕様（期待動作）は決まっているが、自動検証がまだ
      ないもの。コードの有無とは別
    - **実機必須**：2台実機のリアルタイム到達・プッシュ実配送・
      実機キーボードなど、原理的に自動化できないもの
- 新しい仕様を決めたら、まずこの表に行を足し、次に検証を起こす。
  行を足すときに「相手・第三者の画面」列を空欄のままにしない
  （変化なしなら「変化なし」と書く）。

## 未定義リスト（期待動作が決まっていない論点）

記録に決定がないため上の表に入れなかったもの。仕様を決めたら
表へ移し、検証を起こすこと。

1. **キックされた人の再入室**：キック後に同じ部屋へ再参加できるか
   （部屋バンのような再入室制限を付けるか）が決まっていない。
   現実装はメンバー行を消すだけで再参加を妨げないが、それが仕様
   として確定した記録はない
2. **ゴースト掃除で消えた本人の画面**：心拍途絶＝アプリを閉じた
   前提だが、バックグラウンドで5分以上止まった後に復帰した時、
   その人の画面がどうなるか（キックと同じトーストを出すのか等）
   が決まっていない
3. **グループ発言の確定ライン**：DMのみ緩和（0.85→0.75）が
   決まっているが、グループ発言にも緩和があるかは記録がない
4. **マスター放置の通報ベース確定**：設計では「そのルームの
   メンバーから通報があり証跡と一致すれば確定」の経路 (a) が
   あったが、実装・決定の記録があるのは (b) 30日以内3回のみ。
   通報経由の確定を入れるかが未決定
5. **虚偽通報への通報機能制限（30日）**：設計 §3.3 にあるが、
   実装の記録がない。決定済みの範囲（重み低下＋警告DM）で
   止めるのか、制限まで入れるのかの確定記録がない
6. **ロビーのルーム一覧の追随**：ロビー滞在中に部屋が満室・
   終了・新規作成された時、一覧が自動で追随するかは決まって
   いない（現行は再取得のタイミングでのみ更新）
7. **課金上限の購入時適用の詳細**：暦月の集計対象（返金・
   チャージバックの扱い）と、上限到達時の画面表示は課金実装
   フェーズで未定義
8. **異議申し立てのシート運用の実地確認**：Apps Script の設置が
   未完了で、シートの Yes/No→反映→結果DM が実運用で回るかの
   期待動作（処理状態の遷移・エラー時の再試行）の確認が済んで
   いない
9. **試合中のDMの扱い**：試合中にDMを開くこと・送ることへの
   制限（送信ロック等）は本家にはあるが、Lite では決定の記録が
   ない
10. **拒否・取消された側への通知**：フレンド申請を拒否／取消
    された側に通知を出すかは記録がない（現行は送った側の表示が
    消えるだけ）
11. **招待プッシュのカテゴリ振り分け**：招待カードはDMの一種
    だが、プッシュ設定の「メッセージ」と「ルーム招待」の
    どちらのカテゴリで止まるかの明記がない
